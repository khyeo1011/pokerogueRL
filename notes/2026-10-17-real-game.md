# Real game and per-run seed: findings

2026-10-17, for issue #3. pokerogue v1.12.1.1 (`bdfbef6`), Node 24.19, Linux.

**Result:** `bridge/run.ts` `startClassicRun(game, seed, ...species)` boots a Classic run with every
harness game change undone and the game's RNG seeded from `seed`. `bridge/test/run.test.ts` checks both.
It stops where `classicMode.runToSummon()` does, so a `Driver` takes over the same way.

## Where the harness changes the game

| Change | Where | Undone by |
|---|---|---|
| Max roll for every battle roll (damage, accuracy, crits, effect chances) | `GameManager` constructor replaces `BattleScene.prototype.randBattleSeedInt` | `restoreRealGame()` puts upstream's body back |
| Mystery encounter rate 0 | `GameManager.initDefaultOverrides()` mocks `MYSTERY_ENCOUNTER_RATE_OVERRIDE` | `restoreRealGame()` restores the mock |
| No shinies, IVs 31, Hardy natures | `classicMode.runToSummon()` sets the overrides, unless its `override.*` flags are off | not calling `runToSummon()` |
| Enemy starting items removed | `classicMode.runToSummon()` calls `removeEnemyHeldItems()` | not calling `runToSummon()` |
| Seed `"test"` on every run | `generateStarters()` assigns `scene.seed` directly | `setSeed(seed)` after it |

`randBattleSeedInt` gets a copy of upstream's body, not a saved original. pokerogue's vitest config uses
`isolate: false`, so a `GameManager` from an earlier test file may already have replaced the prototype
by the time `bridge/run.ts` is imported.

## Seeding

Upstream, `scene.reset()` picks a random seed (`randomString(24)`, from `Math.random`). `setSeed()` stores
it and derives `waveCycleOffset` and `offsetGym` (the latter reads `gameMode`). `resetSeed()` sows
`Phaser.Math.RND` from it, and `newBattle()` calls `resetSeed(waveIndex)` at the start of every wave.

`startClassicRun` needs two calls, one on each side of `generateStarters()`:

- `setSeed(seed); resetSeed()` before: the starters draw IVs, natures and shininess from `RND` while
  `generateStarters()` runs. Without this they come from `reset()`'s random seed.
- `setSeed(seed)` after: `generateStarters()` sets the seed to `"test"`. `newBattle()` (wave 1) runs
  later, in a `.then()` inside `initBattle()`, and reads the seed.

With both, the same seed gives the same species, IVs, natures and shininess for party and wave-1 enemies.

## Observations

- **One `GameManager` per test.** A second one in the same test throws ("Prompt handler run interval was
  not properly cleared"). Clearing `PromptHandler.runInterval` by hand is not enough: the new
  `PromptHandler` spies on `ui.setModeInternal` again on top of the old spy and overflows the stack.
  vitest's `restoreMocks` and the `afterEach` in `test/setup/vitest.setup.ts` reset both between tests.
  The bridge server will play many runs per process, so it will need its own reset between runs.
- **Unseeded randomness left:** `randInt` (`Math.random`) picks trainer gender and evil-team grunt
  doubles in `getRandomTrainerFunc` (`src/battle.ts`). The rest of gameplay uses the seeded `RND`.
  Same-seed runs can diverge once such a trainer appears.
- **Mystery encounters are now on** (Classic waves 10–180). The driver has no decisions for them yet, so
  a run that reaches one waits forever (#7, #9). `bridge/test/driver.test.ts` still boots through the
  harness, so it is unaffected.
